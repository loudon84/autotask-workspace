## 一句话

到点从手写死循环，改成引入 **APScheduler**。

和 Java 里 `while (true) { sleep; 判断时间; }` 做定时，后来改成 Spring `@Scheduled` / 调度框架，是同一件事。产品还是调度中心；变的是谁负责「到点」。

---

## 背景

调度中心已经定过：独立定时器，名称、开关、5 段 cron，改完热生效；到点只 `notify` 指向。清场后进程里只留一条到点循环。

这条循环是手写的：自己解析 cron、自己 `datetime.now()`、每 30 秒醒一次。FastAPI 不管钟，相当于 Java 里没接 Spring 调度、自己写死循环。

---

## 碰到了什么问题

运维按北京写 `5 9 * * *`，打开后到点不响。

1. 死循环用主机时区。4520 是 UTC 时，上午九点（北京）不会到点。
2. 到点晚一分钟，这一拍直接丢。
3. 再补 `now_china()` 还是死循环，不是框架。

作废排重 / 匹配 409 不在本文。

---

## 引入什么

**APScheduler 3.x**（Python 里常用的进程内调度库）：`AsyncIOScheduler` + `CronTrigger`，时区 `Asia/Shanghai`。

对应关系：

| | Java | 本服务 |
| --- | --- | --- |
| 之前 | 死循环 sleep 做定时 | `TimerScheduler` 30 秒 tick + 手写 `CronSchedule` |
| 现在 | 引入 Spring 调度 | 引入 APScheduler |
| 业务 | `@Scheduled` 里调自己的方法 | 到点仍 `notify(target)`，入口不改 |

删掉手写开火路径。`timers` 启用行同步进 APScheduler；改开关 / cron 热加载。不迁库、不改页面、不改任务入口。库里仍存 crontab（周 `0`/`7`=周日），`from_crontab` 前过垫片。同一 cron 不每 30 秒重挂，以免冲掉 2 分钟 misfire。

不补跑整拍；本拍晚不超过 2 分钟仍算本拍。同一 `target` 不叠跑。

不选 Celery Beat / 系统 crontab（多一个运行时）。本次不用 APScheduler 4。

依赖：`apscheduler>=3.10,<4`，Windows 加 `tzdata`。

---

## 为什么引入、能解决什么、好处

为什么：死循环给不出「按北京时间到点」。框架负责 cron、时区、触发；我们只管登记和 notify。

能解决：`5 9 * * *` 是北京 09:05；「下次触发」和开火同一套；晚一两分钟不丢本拍。不解决扫单/登录对不对、作废后能否再匹配。

好处：小时口径固定北京；不再自己维护 cron 解析；回滚退代码重启即可，无 DDL。

## 不改 / 验收

不改：父文档产品、`target`、入口、已有开关和 cron、立即执行、Client、表结构。禁止再写一套死循环；禁止本次迁正式库。

验收：北京时间两分钟后能到点并有 `timer_runs`；UTC 机器上 `5 9 * * *` 下次是北京 09:05；开火不再走 `CronSchedule.next_after`。

已按本文改代码。库里仍存 crontab 5 段；第 5 段（周）交给 APScheduler 前做数字→英文名垫片（`0`/`7`=周日）。同一 cron 不每 30 秒重挂 job，以免冲掉 2 分钟 misfire 宽限。
