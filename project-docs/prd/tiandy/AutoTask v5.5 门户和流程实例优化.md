---

## 0. 一句话

客户分类（天地伟业 / 京东方）**代码写死**；用户建门户时必选分类。流程实例菜单和 SOP **按分类 code 关联**，不靠用户维护「父门户」或「流程目录」。一期只改天地伟业侧的展示和过滤，现网单据、Binding、调度继续跑。

---

## 1. 为什么要改（现网问题）

现在只有天地伟业在跑，但模型已经按「一个客户 = 一个门户 = 侧栏两条写死菜单」焊死：

- 侧栏硬编码「天地伟业-客户订单 / 对账单」，路由 `/processes`、`/process-instances/statements`
- 门户没有「这是哪家客户」字段；`entityType` 只是客户/供应商，不能当家族
- 正式环境已有多条天地伟业门户（演示 test、正式演练、正式芯云等），实例挂在各自 `portal_account_id` 上
- 手动扫单会遍历**所有启用门户**；生成对账单曾用门户名是否包含「天地伟业」来猜。京东方门户一建，这些会误扫或误选

京东方是「一个分类、多个子公司门户、一套通用流程」。不先把分类从门户里拆出来，发票箱单列表无法知道该聚合哪些门户。

---

## 2. 已定原则

1. **分类写死，门户只打标。** 代码常量：`TIANDI` = 天地伟业，`BOE` = 京东方。显示名可改，code 永不改。
2. **不做用户可维护的父门户表、流程目录表。** SOP、阶段、详情页都是开发按客户写的；再维护一层绑定对不上代码。
3. **流程种类绑分类 code，不绑某一条门户。** 所有 `category=TIANDI` 的门户自动出现在客户订单/对账单里。
4. **叶子门户不变。** 登录、密码、归属人、Cookie、Binding、实例幂等 `(portal_account_id, process_code, biz_key)` 仍在现有 `portal_accounts` / `process_instances`。
5. **一期不交付京东方菜单和发票箱单页面。** 枚举里预留 `BOE`，避免二期再加列。

---

## 3. 代码注册表（功能从哪来）

Task 与 Client 共用同一份语义（实现时可各写一份常量，code 必须一致）：

```text
TIANDI  天地伟业
  ├── srm_customer_order        客户订单   /processes
  └── srm_tiandi_statement      对账单     /process-instances/statements

BOE     京东方          ← 一期只出现在门户下拉，不出现在侧栏
  └── srm_boe_invoice_packing   发票箱单   （二期）
```

侧栏按这份表生成：

```text
流程实例
└── 天地伟业
      ├── 客户订单     → 现网 /processes（不改路径）
      └── 对账单       → 现网 /process-instances/statements（不改路径）
```

一期不渲染「京东方」。二期加发票箱单条目即可，不必再迁门户表。

扫单、回签、建单等 **WorkflowBinding 仍按门户一条条绑**（现网已如此）。分类只回答「这份 SOP 属于哪家客户」，不替代 Binding。

## 4. 数据怎么改（兼容已上线）

`portal_accounts` 增加 `category`（varchar，存 `TIANDI` / `BOE`）。

**正式库回填：现有全部门户写成 `TIANDI`。** 一期上线前只有天地伟业门户，这样现网实例、任务、调度的门户指针都不用动。

列约束建议：

- 迁移：加列 → 回填 `TIANDI` → 再 `NOT NULL`
- 迁移过程可用 `server_default='TIANDI'`，回填完成后可去掉 default（避免以后漏选分类还默默进天地伟业）
- **旧版 Client** 创建/编辑门户若不传 `category`：一期 API **缺省当 `TIANDI`**，避免未升级的安装包建出门户失败或分类为空
- 新版 Client：下拉必选；编辑已有天地伟业门户时带出 `TIANDI`

不改：

- `process_instances` 表结构、`process_code`、唯一键
- 已有 Binding、调度 job、Flow 版本
- 门户名称唯一约束、密码、归属人

DDL 仍须口头授权后才执行。未授权不得迁生产库。

## 5. 一期要做的产品行为

### 5.1 门户

- 新建/编辑增加「分类」下拉：天地伟业 / 京东方（存 code）
- 列表、详情展示分类
- 分类选错：该门户会从对应流程菜单里消失；不自动改 Binding。客服改回分类即可，实例还在原门户上

### 5.2 流程实例菜单

- 「流程实例」下挂「天地伟业」，再挂客户订单、对账单
- 列表页标题可改为「客户订单」「对账单」，不必再把「天地伟业-」焊进每一条菜单文案（分组已经表达客户）
- **旧书签、旧 Client 直开 `/processes` 必须仍能用**

### 5.3 过滤（为京东方预留，一期先修现网隐患）

| 入口 | 现在 | 一期 |
| --- | --- | --- |
| 客户订单列表 | 按 `process_code`，门户不过滤分类 | 只展示门户 `category=TIANDI` 的实例（回填后与现在集合相同） |
| 对账单列表 | 同上 | 同上 |
| 手动扫单 | 所有 `ENABLED` 门户各扫一次 | 只扫 `ENABLED` 且 `category=TIANDI` 且已有扫单 Binding 的门户 |
| 定时扫单 | 已有扫单 Binding 的启用门户 | 再加 `category=TIANDI`（双保险；回填后行为与现在相同） |
| 生成对账单选门户 | 名称包含「天地伟业」等启发式 | 改为 `category=TIANDI` 的启用门户 |

回填完成前不要发「按分类过滤」的 Client/Task 到生产。顺序见 §7。

### 5.4 分类文档（操作手册）

操作手册不属于某一条门户，属于分类：天地伟业多门户共用 `AutoTask天地伟业操作手册.doc`，京东方以后同样一份。

- **分类仍不建名称表。** 和门户 `category` 一样，文档行只存 code（`TIANDI` / `BOE`），合法值以代码注册表为准。
- Client「管理中心 → 门户分类」列出写死的两个分类；点进去上传 / 下载 / 删除文件。登录用户都可以维护，不做单独权限。
- 每个分类可多份文件。文件落在 **Task 应用服务器** `ARTIFACT_LOCAL_DIR/category-docs/{tenant}/{category}/{id}.ext`，不进 Git、不放 Client。
- 表 `category_documents`（迁移 `a1c3e5f70824`）。允许 `.doc/.docx/.pdf/.xls/.xlsx/.ppt/.pptx/.txt/.zip`，单文件 ≤20MB。

不做：在线预览、版本树、按门户挂文档、新开文件服务。

## 7. 上线顺序（天地伟业已在跑）

现网客服每天用客户订单、对账单。发布必须 **Task 迁库回填先于「按分类过滤」的逻辑生效**。

1. **先迁库（授权后）**：加 `category`，全部现网门户回填 `TIANDI`。此时旧 Client 不认识该字段也无妨。
2. **再发 Task**：API 读写 `category`；缺省 `TIANDI`；列表/扫单按分类过滤（过滤集合 = 回填后的全集）。
3. **再发 Client**：门户下拉 + 侧栏两级；路由不变。
4. **验收（正式库只读核对 + 演示库点选）**
   - 客户订单、对账单条数与迁库前一致
   - 打开已有实例详情、手动扫单、定时扫单、生成对账单选门户
   - 新建门户不选分类：旧包仍能建（服务端 TIANDI）；新包必选
5. 回滚：Client 回旧包侧栏变回扁平，路由仍在；Task 回滚前不可丢列（已回填的 `TIANDI` 可留）。过滤逻辑若有问题，可临时只认 `process_code`、不认分类。

不要在未回填时先发「只显示 TIANDI」的 Task：分类为空的门户会从列表消失。

## 附录：原始需求记录

### 背景

之前只有一个天地伟业，所以流程实例和门户强绑定写死，现在多个门户多个流程实例就很乱了。

### 一、门户分层（父门户）

天地伟业对我们是一个客户；京东方在系统里是多个独立子公司门户。发票箱单是针对所有京东方子公司的通用功能，必须能区分哪些门户是京东方。

### 二、流程实例分多级菜单

```text
流程实例
├── 天地伟业
│     ├── 客户订单
│     └── 对账单
└── 京东方
      └── 发票箱单
```

### 三、分类写死比维护好

功能是开发时就知道属于天地伟业还是京东方的，不能等用户维护门户才决定有什么功能。代码写死分类键值对；用户维护门户必选分类；流程实例按分类 code 强制关联，不靠用户维护的抽象目录。
