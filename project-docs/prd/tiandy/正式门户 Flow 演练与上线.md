# 正式门户 Flow：演练与上线同一份包

| 项 | 内容 |
| --- | --- |
| 状态 | 架构规则仍有效；**演练/上线怎么配、现在能点什么见 [v4.1 SOP](./AutoTask%20v4.1%20天地伟业正式演练与上线SOP.md)** |

| 基线 | [v4.0 正式演练](./AutoTask%20v4.0%20天地伟业正式演练.md)；演示门户仍用独立包（`data-rpa`），本文不合并 |

---

## 1. 要解决什么

演示站与正式站页面不同，**本来就该两套 Flow 版本**，按门户 Binding 各绑各的。这不是本文的问题。

问题是：正式演练要把 SOP 跑通（当前常没有待签章），真上线又必须是「待签章查询 → 导出 Excel → 建任务」。如果演练另做一包、或在 `flow.py` 里写死样例单号，上线还要改包。

真用阶段会跟客服操作一段时间，改选择器和条件几乎难免。架构上要让这类改动落在 **Binding / 选择器 / 小版本**，而不是再分「演练包 / 上线包」。

---

## 2. 规则

1. **正式演练和真上线共用同一份正式 Flow。** 同一个 `rpaFlowId`，版本只往上加（`1.1.2` → `1.1.3`）。Binding 钉死正在用的版本，旧版留着回滚。
2. **Flow 只实现真上线那条操作。** 演练用 Binding 把数据和闸喂进去，好把整条 SOP 跑通。不要为演练做「假成功、不进页面」的包。不要在 Task 里对空结果造订单。
3. **样例单号、是否当成待签章、是否点 SRM 提交，都不进 `flow.py`。** 进该门户的 `WorkflowBinding.config`。上线改配置，不换包。
4. **跟用户操作对齐时，优先改 Binding 条件和 `selectors.json`，再发小版本。** 不为演练/上线再拆一条产品线。

演示门户 Binding 继续指向演示包。禁止把正式包绑到演示 URL，也禁止把演示 `data-rpa` 包绑到正式站。

---

## 3. 扫单（客户订单入口）

真上线永远是：

1. 按条件填表（回复状态=待签章，无其它条件）
2. 查询
3. 导出 Excel
4. 用 Excel 建后续客户订单任务

演练不要另写一套。把「再搜一次」做成**同一套填表→查询→导出**的后续尝试，条件来自 Binding：

```json
{
  "searches": [
    { "replyStatus": "待签章" },
    { "poNo": "POJS2607170008", "treatAsPending": true }
  ]
}
```

| 阶段 | Binding | 行为 |
| --- | --- | --- |
| 正式演练 | 上面两条都配 | 没待签章则按订单编号再导出，把该单当成待签章扫入（不改 SRM 状态） |
| 真上线 | 只留第一条 | 没待签章就是空列表成功，不再拿样例单往下走 |

`treatAsPending` 只允许出现在演练 Binding。生产 Binding 不得把已回签改写成待签章。

---

## 4. 其它节点同样拆

| 步骤 | Flow 里只做（上线也是这个） | 演练用 Binding / 环境，不上新包 |
| --- | --- | --- |
| 扫单 | 填条件 → 查询 → 导出 → 解析 | `searches` 多一条单号 |
| 建 SDMS | 打开 PO → 下载订单 → 写 SDMS | SDMS 地址走 Task `.env`（测试/生产）；Binding **不设** `dryRun` |
| 填交期 / 签章 / 生成对账单 / 提交审核 | 真点到按钮 | `dryRun: true` 停在对 SRM 的提交前；上线改为 `false` 或删除该键 |
| 下合同 | 下载已回签合同 → 上传 SDMS | SDMS 测试环境真写；上线换 `.env` 基址 |

`dryRun` 只拦对正式 SRM 的写，与 v4.0 三道写闸一致。

---

## 5. 明确不做

- 演练包 / 上线包各一份正式 Flow
- `flow.py` 里 `if drill` 或默认写死 `POJS2607170008`
- 扫单空列表时由 Task 合成订单
- 把演示 `data-rpa` 包绑到正式站
