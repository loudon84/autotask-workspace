## 2. R1：演示门户签章状态现象（事实说明）

### 2.1 现象

在当前演示门户上：

1. 客服/RPA 发起「签章」后，**当前浏览器页**回复状态往往直接变成 **「已回签」**（而不是规范流程中的「待回签」）。
2. **没有后端落库**：该状态仅存在于当前页面会话；刷新、重新登录或新开浏览器后，可能仍回到「待签章」或丢失交期（与 v2.01 / 未决#14 一致）。

### 2.2 对产品契约的含义

| 环境 | 期望 |
|------|------|
| 正式 / 可落库门户 | 签章成功 → SRM **待回签** → 双方线下签完 → SRM **已回签** |
| 演示门户（现状） | 页面可能跳过「待回签」直接显示「已回签」，但不可靠；**不能**把「页面上闪过已回签」当作跨会话真相 |

v2.02 轮询与自动归档必须以 **可回读的 SRM 回复状态**（或明确的 TEMP 联调策略）为准；演示不落库未修复前，自动链路仍可能扫不到真实「已回签」。

## 3. R2：待回签 → 已回签 自动轮询并归档（核心变更）

### 3.1 相对 v2.01 的流程对比

**v2.01（人工）**

```text
节点3 去签章 SUCCESS → SIGN_REQUESTED（待双方签章）
        ↓
客服线下确认 SRM「已回签」
        ↓
客服点「已签章订单下载」→ 节点4 RPA → ARCHIVED
```

**v2.02（自动）**

```text
节点3 去签章 SUCCESS → SIGN_REQUESTED（系统侧：待回签/待双方签章）
        ↓
[回签轮询作业] 每 30 分钟
  拉取阶段=SIGN_REQUESTED 的流程实例
  对每单查 SRM 回复状态
        ├─ 仍为「待回签」→ 跳过，等下轮
        └─ 已为「已回签」→ 推进 SIGNED（或等价）并自动创建节点4子任务
                ↓
        节点4 RPA：下载签章版合同 → 上传 SDMS → ARCHIVED
```

### 3.2 产品规则

| 项 | 规定 |
|------|------|
| 轮询间隔 | **30 分钟**（可配置，默认 1800 秒）；列表提供 **「立即回签轮询」** 手动触发一整轮，不等待定时器 |
| 轮询范围 | `status=ACTIVE` 且阶段为 **`SIGN_REQUESTED`（待回签）或 `DATES_COMPLETE`（待签章）** 的流程实例（可按租户/Portal 分批）。放宽待签章是为演示门户 TEMP：种子单在 SRM 已是「已回签」、AutoTask 仍停在待签章时可被探测到并归档；正式门户待签章单通常不是已回签，多一次只读探测可接受 |
| 外部判定 | 以 SRM 订单回复状态 **「已回签」** 为进入下一节点条件 |
| 发现后动作 | **先**将流程实例阶段推进为 **已回签**（`SIGNED`），**再**自动创建归档子任务（下载双方签章合同 + 上传 SDMS） |
| 人工按钮 | 「立即回签轮询」（列表）。「手动触发签章合同下载」**仅**在 `SIGNED`（已回签）作归档失败重试；**待回签阶段不提供** |
| 幂等 | 同一实例不得因轮询重复创建多个并发归档子任务；已有进行中/成功的归档子任务则跳过 |
| 失败 | 归档子任务失败：实例保留在可重试状态（阶段与错误码按现有失败策略），下轮轮询或人工兜底可再触发（需幂等） |

### 3.3 与签章子任务成功瞬间的衔接

| 情况 | 行为 |
|------|------|
| 签章 Run 成功（无论当时读到「待回签」还是「已回签」） | **一律**停在 `SIGN_REQUESTED`（待回签）；**不**在签章成功回调里触发节点4 |
| 演示门户瞬间闪「已回签」 | 不可信（常不落库）；仍停在 `SIGN_REQUESTED`，等轮询读到可回读的「已回签」再归档 |
| 签章 Run `WAITING_HUMAN` / 状态未确认 | **不**自动归档；保持现有人工/重试语义；实例可仍停在待签章 |

节点4（已签章下载上传）主路径：由回签轮询发现 SRM「已回签」后自动触发；候选含 **待回签 + 待签章（演示 TEMP）**。列表「立即回签轮询」可立刻跑一轮。

**待回签含义**：发起签章后，客户（如天地伟业）盖章 → 我司盖章，整段过程均为待回签；此阶段**不得**下载/上传签章合同。仅 SRM 变为「已回签」后实例阶段**立刻**变为已回签，再做合同下载上传；详情「手动触发签章合同下载」只作已回签阶段失败重试。

### 3.3A 演示门户联调说明（TEMP）

- 当场签章不落库 → **不能**用刚签的那单验「待回签→已回签」轮询。
- 应用门户初始化里**本来就是「已回签」**的订单：扫单/建单后实例可停在 `DATES_COMPLETE`，点「立即回签轮询」→ 探测到已回签 → 自动归档。
- 门户可持久化后，候选可再收紧为仅 `SIGN_REQUESTED`（另开增量）。

### 3.4 实现落点（供计划拆分，非实现细节定稿）

- service：仿 `ScanScheduler` 增加 **回签轮询调度器**（开关、间隔配置）；只读或轻量 RPA/探测查 SRM 状态，或复用「只查询回复状态」的 Flow/任务。
- 发现已回签 → 更新阶段 + 调用与现 `archive_signed_order` 相同的创建子任务逻辑（去掉「必须人工」门禁，或内部复用）。
- Client：详情阶段文案改为「系统轮询回签中」类提示；主按钮不再强调人工下载（兜底可保留）。

### 3.5 明确废止 / 覆盖的 v2.01 条文

- v2.01 §4 节点4「进入条件：客服确认已回签后点按钮」→ **改为轮询自动**。
- v2.01 §9「第一期不自动扫待回签→已回签」→ **v2.02 起改为自动扫**。
- v2.01 §10 候选「P2 自动扫已回签」→ **升为 v2.02 正式需求 R2**。

## 3A. R3：节点4附件对象纠正（双方签章合同）

### 3A.1 正确业务

| 项 | 规定 |
|------|------|
| 时机 | SRM 回复状态为 **「已回签」** 之后 |
| 下载对象 | **双方签章合同**（演示门户：详情「查看签章」触发下载的 PDF 等合同文件） |
| 上传目标 | SDMS 销售订单 **附件** |
| 明确禁止 | 不得把门户「下载订单」得到的订单 XLSX / XML / 明细导出当作本节点附件 |

### 3A.2 与既有实现差异

历史 Task 3 Flow `1.0.x` 点击「下载订单」并上传订单文件，**不符合本条**。v2.02 起归档 Flow 须改为「查看签章 → 合同文件 → SDMS 附件」。

### 3A.3 SDMS 附件上传接口（R4）

测试环境：

```text
POST http://192.168.99.111:8080/core/api/srm/so/uploadAttachment
```

| 项 | 规定 |
|------|------|
| 认证 | 与「创建 SDMS 销售订单」相同：先 `POST /core/oauth/token`（client_credentials），上传时带 `Authorization` |
| `flag` | **`SDMS_SO1`（固定）** |
| `custPoNumber` | 客户订单号（Flow 输入 `po_no`） |
| `uploadUrl` | **必填**。测试环境固定 `http://api.doc.uat.smart-core.com.hk/upload`（文档服务上传地址，不是文件下载 URL） |
| `username` | Auth 登录账号（SDMS 工号）。Task 从当前请求 `/me.username` 写入 Flow 输入；轮询归档回退 UserCache.name |
| `filename` | 客户订单号 `po_no` |
| `file` | 双方签章合同文件 |

实现：Flow `rpa_flow_supplier_portal_upload_order_attachment` **1.2.2**。缺 `uploadUrl` 时接口返回「上传地址不能为空」。`username` 为当前 Auth 登录账号（SDMS 工号），不写死。新接口未提供附件列表，不再对旧附件服务做查询幂等。Token 与 Authorization 不得写入日志或 Artifact。

## 4. O1：子任务与执行记录改为树状

### 4.1 问题（v2.01）

详情「子任务与执行记录」为**扁平列表**。同一节点多次失败重试时，列表被大量同阶段任务淹没，难以一眼看到：

- 当前卡在哪一节点；
- 哪一行交期在重试；
- 哪次是有效成功路径。

### 4.2 目标（v2.02）

改为 **树状结构**（UI 可用展开/折叠）：

```text
流程实例
├─ ① 建 SDMS
│   ├─ 最新/成功 Run …
│   └─ 历史失败尝试（默认折叠）
├─ ② 填写交货日期
│   ├─ 行 10
│   │   ├─ 当前状态 WRITTEN / 最新子任务
│   │   └─ 失败重试（折叠）
│   └─ 行 20 …
├─ ③ 发起签章
│   └─ …
└─ ④ 已签章下载上传
    └─ …
```

### 4.3 规则

| 项 | 规定 |
|------|------|
| 聚合键 | 节点类型（扫单/建单/填交期/签章/归档）；填交期再按 `line_number` |
| 默认展示 | 每聚合节点展示**最新一次**子任务 + 状态；失败历史默认折叠 |
| 跳转 | 叶子仍可进现有任务/Run 详情查日志与证据 |
| 数据 | 优先用现有 `automation_tasks` + `process_instance_id` / 行上 `sub_task_id` 组装；不强制改表，必要时仅加查询聚合 |

## 5. O2：ERP / SDMS 销售订单超链接

### 5.1 问题（v2.01）

详情在建单成功后展示 `ERP 订单：{orderNumber}` 为纯文本，无法跳到 SDMS 查看单据。

### 5.2 目标（v2.02）

- 展示文案仍可用订单号（如 `10408260800013` / `orderNumber`）。
- 该文案为**超链接**，打开 SDMS 销售订单查看页。

### 5.3 URL 约定

测试示例：

```text
http://192.168.99.35:8080/sdms/om/sdms_om_main/sdmsOmMain.do?method=view&fdId=1100983
```

| 部分 | 来源 |
|------|------|
| 协议+主机+端口（及可选上下文根前缀） | **可配置**，如 `SDMS_WEB_BASE_URL=http://192.168.99.35:8080/`；测试可先写死默认值 |
| 路径与 query | 固定：`sdms/om/sdms_om_main/sdmsOmMain.do?method=view&fdId={headerId}` |
| `fdId` | 建单回传中的 **`headerId`**（不是 `orderNumber`，不是 `sourceHeaderId`） |

建单回传示例字段（节选）：

```json
{
  "orderNumber": "10108260700027",
  "sourceHeaderId": "19cfa8ffff403cd3267ab59436abc746X2e",
  "headerId": "1091975",
  "soStatus": "BOOKED",
  "soApprovedStatus": "NEW",
  "processGroupId": "1784172232212",
  "processStatusCode": "COMPLETE",
  "processMessage": "&MESSAGE (MESSAGE=)"
}
```

### 5.4 数据与配置

| 项 | 规定 |
|------|------|
| 持久化 | 节点1成功写入 `process_instances.summary` 时增加 **`headerId`**（及可选保留 `orderNumber` 等现有字段） |
| 历史数据 | 无 `headerId` 时不渲染链接，仅显示订单号文本 |
| Client | 详情（及交期页若展示 ERP 订单）用 `base + path + headerId` 拼链接；`base` 来自配置（Client 设置 / 远程配置 / 构建默认），测试环境可用上述地址 |
| 打开方式 | 系统浏览器或应用内 Web 页均可，实现时与现有外链习惯一致 |

## 6. O3：流程实例阶段与总状态表达（体验澄清）

### 6.1 问题（联调反馈）

客服在列表/详情看到两套「状态」文案，含义不清：

| 界面位置 | 当前常见文案 | 实际字段 |
|----------|--------------|----------|
| 列表 Tab / 「阶段」列 | 建单中、待填写交期、交期填写中、待签章、待回签、已回签、已完成、失败 | `stage` |
| 列表「状态」列 / 详情角标 | 进行中、失败（及已完成、已取消） | `status` |

典型误判：节点3签章子任务 `WAITING_HUMAN` / 失败后，实例仍为 `stage=DATES_COMPLETE`（待签章）+ `status=ACTIVE`（进行中）。详情顶部只强调「进行中」，**看不出卡在签章、也不突出最近错误**，只能自己翻子任务树。

根因不是「少了一种总状态」，而是：

1. **产品上本就有两维**：SOP 进度（`stage`）与实例生死（`status`）；
2. **UI 把两维都叫「状态」**，且失败子任务默认**不抬**实例 `FAILED`（便于重试），顶部又未展示卡点。

### 6.2 设计原则（推荐方案）

**保留两维模型，不合并成单一枚举**（合并会丢掉「停在待签章但仍可重试」与「整单已死」的区别）。

| 维度 | 字段 | 对人的一句话 | 取值（与实现枚举对齐，文案见下表） |
|------|------|--------------|-----------------------------------|
| **当前阶段** | `stage` | 这单 SOP 卡在哪一步 / 下一步该干什么 | 建单中 → … → 待回签 → … → 已完成；另有阶段失败态 |
| **运行总状态** | `status` | 这单还能不能继续推进 | 进行中 / 已完成 / 失败 / 已取消 |

推荐（相对另两种方案）：

| 方案 | 做法 | 取舍 |
|------|------|------|
| **A（推荐）** | 保留 `stage`+`status`；统一文案；详情**阶段为主、总状态为辅**；增加「卡点/最近错误」条 | 改 UI/文案为主，状态机基本不动 |
| B | 子任务一失败就把实例 `status/stage` 打成 FAILED | 顶部好认，但可重试路径被「整单失败」语义污染，需大量改重试门禁 |
| C | 取消 `status`，只留 `stage` | 模型变简单，但「取消」「整单失败 vs 阶段失败」仍要另造字段，收益小 |

**本版采用 A。** 状态机规则（签章失败不自动 FAILED、成功才进 `SIGN_REQUESTED` 等）默认**不变**；O3 以 Client 表达 + 错误可见性为主。若后续要把「签章 WAITING_HUMAN」升为显式实例级「阻塞」枚举，单开增量，不在本条默认范围。

### 6.3 文案对齐（列表 Tab = 详情阶段名）

同一 `stage` 在列表筛选 Tab、列表「阶段」列、详情进度条上**必须同一中文名**（禁止再出现 Tab「待签章」、进度条「发起签章」两套叫法）。

| `stage` | 统一中文名（对人） | 说明 |
|---------|-------------------|------|
| `CREATING_SDMS` | 建单中 | 节点1 进行中 |
| `SDMS_CREATED` | 待填写交期 | 建单成功，尚未填行 |
| `DATES_PARTIAL` | 交期填写中 | 部分行已写入 |
| `DATES_COMPLETE` | 待签章 | 交期齐，可发起签章 |
| `SIGN_REQUESTED` | 待回签 | 已发起签章，系统轮询 / 待双方完成；详情可附一句「系统轮询回签中」说明，**不另造 stage 名** |
| `SIGNED` | 已回签 | 轮询/确认 SRM 已回签；随后自动（或手动重试）下载双方签章合同上传 SDMS |
| `ARCHIVED` | 已完成 | 与 `status=COMPLETED` 同时出现 |
| `FAILED` | 失败 | 与 `status=FAILED` 同时出现（整单失败） |

`status` 中文名保持：`ACTIVE`→进行中，`COMPLETED`→已完成，`FAILED`→失败，`CANCELLED`→已取消。  
列表列头建议显式区分：**「阶段」** / **「运行状态」**（勿两列都叫「状态」）。

### 6.4 详情页信息架构

```text
[ 标题：流程实例 {bizKey} ]
[ 主徽章：当前阶段（如「待签章」） ]  [ 辅徽章：运行状态（如「进行中」） ]

（可选）卡点提示条 —— 仅当存在「未清掉的失败/待人工」时显示：
  「签章未完成：Order reply status was not confirmed after sign」
  + 错误码 + 链到对应子任务/Run（若有）

[ 流程进度条：与上表统一的阶段名 ]
[ 摘要：PO / ERP 订单 / 供应商 … ]   ← 此处不再单独用「状态：进行中」抢主视觉
[ 订单行 ]
[ 子任务树（O1）]
[ 阶段历史 ]
```

#### 卡点提示条触发条件（产品规则）

满足任一则展示（优先级从上到下取一条主文案即可）：

1. `status=FAILED` 或 `stage=FAILED` → 展示整单失败（`lastError*`）。
2. 否则若 `lastErrorCode` / `lastErrorMessage` 非空，且当前阶段仍为可重试业务阶段（如仍停在待签章）→ 展示「当前阶段阻塞：{message}」。
3. 否则若存在该实例下**最新相关**子任务为 `FAILED` / `WAITING_HUMAN`（签章、建单、归档、按行填交期等）→ 展示「{节点名}未完成：{子任务错误或状态}」。

消失条件：用户成功重试并推进阶段，或错误被新的成功 Run 覆盖清空（与现有 `lastError*` 清理策略一致）。

#### 与按钮区关系

主操作按钮仍由**当前阶段**决定（填写交货日期 / 去签章 / 手动触发已签章下载 / 重试）。  
卡点提示条**不替代**按钮，只解释「为什么还停在这」。

### 6.5 列表页

| 项 | 规定 |
|------|------|
| 筛选 Tab | 继续按 `stage`（文案用 §6.3） |
| 「阶段」列 | `stage` 中文名 |
| 「运行状态」列 | `status` 中文名；`ACTIVE` 且存在卡点（有 `lastError*` 或最新关键子任务失败/待人工）时，可用次要样式或小标记「有阻塞」，避免仍只显示「进行中」造成误判 |
| 操作列 | 仍按阶段给按钮；有阻塞时按钮文案可保持「去签章」等，由详情卡点条解释原因 |

列表「有阻塞」标记若首期成本高，可先做详情卡点条，列表仅改列名与阶段文案统一；但**详情卡点条为本条必做**。

### 6.6 明确不做（O3 边界）

- 不把 `WAITING_HUMAN` 默认写成实例 `FAILED`（除非另开需求改状态机）。
- 不删除 `status` 字段。
- 不要求本版新增第三套「阻塞状态」持久化枚举（卡点由 `lastError*` + 子任务状态推导即可）。

## 7. O4：客户订单命名与导航（门户定制 SOP）

### 7.1 背景

客户订单流程实例**不是**跨门户可复用的通用 SOP：字段、阶段与门户契约按客户定制。换一个 portal 不能指望同一套模板「自适应」。因此：

- 导航与页面文案明确为「客户订单流程实例」；
- 「客户」展示取门户的 **`portal_name`**；
- 本门户相关 WorkflowTemplate **名称直接带客户标注**（如 `天地伟业·创建 SDMS 销售订单`）。

### 7.2 侧栏

```text
流程实例（可折叠）
  ├─ 客户订单流程实例   → /processes
  └─ 对账单流程实例     → /process-instances/statements（本期占位页，字段后续另开）
```

### 7.3 客户订单 UI 文案

| 原 | 现 |
|----|----|
| 流程实例（列表/详情标题） | 客户订单流程实例 |
| 采购订单 / PO | 客户订单 |
| 供应商 | 交易主体（我司，取 `summary.supplierName`） |
| （无客户列） | 客户 = `portal_name`（按 `portalAccountId` 解析） |

新建实例标题：`{portal_name}·客户订单 - {po_no}`。

### 7.4 流程模板命名

对本客户门户 Binding 下的客户订单相关模板（扫单 / 建 SDMS / 填交期 / 签章 / 回签探测 / 附件上传），名称统一为：

`{客户标注}·{节点中文名}`，例如 `天地伟业·订单回签`。

不在本版做「按 portal 自动改名」的平台能力；换客户 = 另配模板与 Binding。

### 7.5 明确不做（O4 边界）

- 不对账单流程字段与状态机（仅导航占位）。
- 不把客户订单 SOP 改造成跨门户通用流程引擎。

## 9. 验收要点（实施后）

1. **R2**：`SIGN_REQUESTED` 实例在 SRM 变为「已回签」后，不超过一个轮询周期（默认 30 分钟）内自动进入归档并上传成功（或进入明确失败态）；客服无需点主按钮即可完成主路径。
2. **R2**：同一实例不会因轮询重复堆积多个归档子任务。
3. **O1**：详情子任务区按节点（及交期按行）树状展示；多次失败不造成主路径不可读。
4. **O2**：建单成功且 summary 含 `headerId` 时，「ERP 订单」可点开并落到正确 SDMS 查看页；更换配置基址后链接主机可变、`fdId` 仍为 `headerId`。
5. **R1**：文档与联调说明中明确演示门户「页面已回签但不落库」的限制，避免误判自动化成功。
6. **O3**：列表/详情对同一 `stage` 使用同一中文名；列头区分「阶段」与「运行状态」。
7. **O3**：签章子任务失败或待人工、实例仍为进行中+待签章时，详情**主展示阶段「待签章」**，并出现卡点/错误提示（不得仅显示「进行中」而无阶段与错误）。
8. **O4**：侧栏可折叠「流程实例」含客户订单与对账单占位；客户订单页客户列来自 `portal_name`；本门户相关流程模板名含客户标注。
