# 流程包开发注册发布与绑定规范

权威开发规则见 [RPA Flow 开发规范](../designs/rpa-flow-development-guide.md)，完整 HTTP 示例见 [Flow 包上传与发布手册](../../rpa-engine/docs/Flow包上传与发布操作手册.md)。

## 开发约束

每个版本至少包含 `manifest.json`、`flow.py`，建议包含 `selectors.json` 和 `tests/`。ZIP 根目录直接放这些文件，不得再包一层同名目录。入口固定为顶层 `async def run(ctx)`。

Flow 只能使用 Engine 注入的 `ctx.page`、`ctx.input`、`ctx.credentials`、`ctx.portal_url`、`ctx.artifacts`、`ctx.events` 和 `ctx.config`。禁止自行启动 browser、连接 CDP、直连数据库、修改 Task 状态、读明文密码文件或绕过 Artifact Recorder。

Manifest 必须包含稳定 Flow ID、SemVer、`PLAYWRIGHT_CDP`、`flow.py:run`、支持的 workflow code、输入 Schema、能力和最低 Engine 版本。输入名称、类型和 required 必须与 Task 模板完全对齐。

## 包与安全

- 默认 ZIP ≤50 MiB、解压后 ≤200 MiB、文件数 ≤500、压缩比 ≤100。
- 禁止绝对路径、`..`、符号链接、加密条目、`.env`、凭据文件和环境专用地址。
- `rpaFlowId + version + scope/tenant` 不可覆盖；内容改变必须升版本。
- 签章、上传等写操作必须幂等；结果不明确时转人工，不盲目重试。
- 截图应等待目标区域稳定渲染后再采集，避免只截到半成品界面。

## 注册发布顺序

```text
GET  /health/ready
POST /api/v1/flows/packages
POST /api/v1/flow-versions/{flowVersionId}/validate
POST /api/v1/flow-versions/{flowVersionId}/publish
GET  /api/v1/flow-versions/{flowVersionId}
POST /api/v1/flow-versions/validate-binding
```

Engine `/api/v1/**` 请求携带 `X-Actor-Id`；TENANT Flow 还带 `X-Tenant-Id`。上传成功只是 DRAFT，发布成功后才可绑定。

## Task 数据顺序

`Portal → Template(启用) → Binding(精确校验并启用) → Task → Run`。

Binding 中 Flow ID 只填 `rpa_flow_xxx`，版本单独填 `1.2.3`，不要写成 `rpa_flow_xxx@1.2.3`。必须保存发布返回的精确 UUID 和 checksum；禁止 latest 回退、占位 UUID、`seed-version-*` 或零 checksum。

登记 Flow ID、版本、scope、workflow code、UUID、checksum、发布人、测试 Task/Run 和结果。Registry 回滚不会自动改 Binding；业务回滚必须显式切到旧版本快照并重新校验。旧版本禁止覆盖或删除。
