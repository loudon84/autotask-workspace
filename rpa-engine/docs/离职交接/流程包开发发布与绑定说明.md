# 流程包开发、发布与绑定说明

## 1. 开发约束

- ZIP 根目录至少包含 `manifest.json` 和 `flow.py`，可包含 `selectors.json`。
- `flow.py` 必须提供顶层 `async def run(ctx)`。
- 当前 `engineType` 为 `PLAYWRIGHT_CDP`，入口为 `flow.py:run`。
- Flow 只能使用 Engine 注入的 `ctx.page`，不得自行启动浏览器或直接连接 CDP。
- Portal 地址来自 `ctx.portal_url`，凭据来自 `ctx.credentials`。
- 不得在包中写入密码、Token、数据库连接串、内网地址或环境专用配置。
- 同一 scope/tenant 下 `rpaFlowId + version` 不可覆盖；内容改变必须提升 SemVer。
- 外部写操作必须设计幂等或“结果不明确时转人工”，不得盲目自动重试。

## 2. Manifest 关键字段

```text
rpaFlowId
name
version
engineType
entrypoint
supportedWorkflowCodes
inputSchema
capabilities
minimumEngineVersion
```

`supportedWorkflowCodes` 必须与 Task 模板 code 对齐。输入名称、类型和 required 必须与 Task 模板输入 Schema 对齐。

## 3. 发布顺序

1. `GET /health/ready`
2. `POST /api/v1/flows/packages`
3. `POST /api/v1/flow-versions/{id}/validate`
4. `POST /api/v1/flow-versions/{id}/publish`
5. `GET /api/v1/flow-versions/{id}`
6. `POST /api/v1/flow-versions/validate-binding`

完整请求示例见 [Flow 包上传与发布操作手册](../Flow包上传与发布操作手册.md)。

## 4. Task 侧数据顺序

```text
Portal
  -> Workflow Template（创建并启用）
  -> Workflow Binding（精确版本校验并启用）
  -> Task
  -> Start
  -> Run
```

Binding 必须保存发布返回的精确：

```text
rpaFlowId
version
rpaFlowVersionId
packageChecksum
```

禁止使用“最新发布版本”回退，禁止使用占位 UUID、`seed-version-*` 或零 checksum。

## 5. 发布验收记录

每个版本至少记录：Flow ID、版本、Flow Version UUID、checksum、scope、workflow code、发布人、发布时间、测试 Task/Run ID 和结果。不要记录秘密或签名 URL。

## 6. 回滚原则

Engine Registry 回滚只调整 Flow 版本状态，不会自动修改 Task 已存在的 Binding。真正的业务回滚需要 Task 显式把 Binding 切换到目标旧版本的精确 UUID/checksum，并重新执行 Binding 校验。
