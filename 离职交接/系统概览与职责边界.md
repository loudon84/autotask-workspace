# 系统概览与职责边界

## 1. 当前基线

- 产品分支：`v0.1`。
- RPA Engine 服务版本：`0.6.0`。
- Python：`3.12`。
- 默认端口：`4610`。
- 数据库：PostgreSQL 数据库 `nodeskclaw_task`，Schema `rpa_engine`。
- 对象存储：S3 兼容存储，用于不可变 Flow ZIP 包。
- 浏览器：Engine 托管的 Playwright Chromium/Chrome/Edge，会话模式为 `MANAGED`。

## 2. 组件职责

| 组件 | 主要职责 | 不负责的内容 |
| --- | --- | --- |
| Auth（4510） | 用户登录、JWT、组织和管理员身份 | Task、Run、Flow 包执行 |
| Task（4520） | Portal、模板、Binding、Task、Run、事件、Artifact 元数据、后继任务 | Flow ZIP 存储和 Playwright 执行 |
| RPA Engine（4610） | Flow Registry、版本校验/发布、Worker、lease、Runtime、浏览器、Artifact 上传、回调 | 用户登录、业务任务创建、任务列表页面 |
| Client | 用户界面、任务维护、证据预览下载、Portal/模板/Binding 管理 | 保存门户密码、直接调度 Worker |
| PostgreSQL | Task 与 Engine 的业务和运行元数据 | Flow ZIP、截图、XLSX 文件本体 |
| MinIO/S3 | Flow ZIP 和按部署方案管理的对象文件 | 用户权限与任务状态机 |

## 3. 运行链路

```text
用户或外部系统
  -> Task 创建并启动任务
  -> Task 创建 QUEUED Run
  -> Engine Worker 轮询 lease
  -> Engine 精确解析已发布 Flow 版本
  -> Runtime 启动 MANAGED 浏览器并执行 flow.py:run(ctx)
  -> Engine 续租、发送事件、上传 Artifact
  -> Engine finish 回调 Task
  -> Task 和 Run 进入终态
```

Engine 没有对外的“立即运行 Flow”HTTP 接口。业务运行入口始终是 Task；Engine 只通过 Worker lease 主动领取 Run。

## 4. 数据归属

Engine 自有九张表位于 `rpa_engine` Schema，包括 Flow、Flow 版本、校验记录、发布审计、Worker、执行尝试、Callback Outbox、浏览器 Profile 和 CDP endpoint。Artifact 元数据归 Task，不是 Engine 九表之一。Task 表位于同一数据库的 `public` Schema。两侧通过 UUID 和 HTTP 契约关联，不允许由应用启动时自动建表或迁移。

Flow 成功时可返回 JSON object。Engine 在 `SUCCESS` finish 中传递经过大小和敏感字段检查的输出；Task 可据此创建后继任务。Flow 返回 `None` 的历史版本仍兼容。

## 5. 稳定性边界

- EVENT 和 FINISH 已通过 `rpa_callback_outbox` 持久化并按至少一次语义重试。
- Task 必须按稳定 `Idempotency-Key` 去重，并结合 `leaseId` 拒绝旧 attempt 的陈旧 FINISH。
- Artifact 上传 URL 请求、对象 PUT 和元数据登记仍是直接调用，尚未进入可靠 Outbox。
- Python Flow 仍在 Engine 进程内执行，没有子进程或容器级隔离。
- `WAITING_HUMAN` 当前为 Type-A：记录证据并结束，人工处理后不能恢复原浏览器会话。

## 6. 修改边界

- Engine API、ORM、迁移和 Runtime 修改在本仓库完成。
- Task 的任务、Binding、lease、回调和 Artifact 下载地址修改在 `nodeskclaw-task` 完成。
- Client 页面和安装包修改在 `copilot-autotask` 完成。
- Flow 业务逻辑在独立 `rpa-flows` 工作区完成，不应直接塞入 Engine 源码目录。
- 生产配置、数据库操作、对象存储管理和 Secret 轮换由对应管理员执行并留痕。
